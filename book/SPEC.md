# Dams in Section: the authoring spec

This is the one document every agent reads before touching the book. It turns the approved plan
(`~/.claude/projects/-Users-ianmacdonald-code-dams-physics/memory/book-plan/final-plan.md`, which overrides
the supporting reports where they differ) into contracts: where every file lives, how the build
assembles them, how numbers and references work, the exact markup of every component, the voice,
and a brief for every chapter. If something here disagrees with a report in `book-plan/`, this spec
wins; section 0.3 lists where I had to decide.

The product is the single page `docs/index.html` (https://ian-macdonald.me/dams-physics/). It stays a
single page. Nothing in this spec changes a solver's physics or an element id.

## 0. Ground rules, roles, decisions

### 0.1 Hard rules (from the user; they override everything else)

1. Edit `src/` (and `tests/`, `book/`) only. `docs/index.html` is regenerated by `python3 build.py`;
   never hand-edit it. Rebuild before you commit and commit `docs/index.html` with your src changes.
2. Element ids of figures, controls and readouts never change. The JS, the tutor and the tests
   depend on them. The full list is in section C.
3. The solvers' physics never changes. Every number the page shows stays exactly what the code
   computes. A technical error you find: fix it with a test only if it is a display or wording
   error; otherwise report it under `concerns` and leave the physics alone.
4. All tests pass after every commit: `node tests/test-figures.js`, `node tests/test-seepage.js`,
   `node tests/test-stability.js`, `node tests/test-academy.js`, `node tests/test-grains.js`
   (about 30 s), and, once it exists, `node tests/test-book.js`. Read each exit code.
5. No ML or AI models run locally. ffmpeg, ImageMagick and headless Chrome are fine.
6. git: stage only the files you changed (`git add <paths>`, never `-A`). Do not push. Never force.
   Short, specific commit messages that end with a blank line and
   `Claude-Session: https://claude.ai/code/session_016BdwbXb5oLmAi8i3y5e21h`.
7. Build in parallel without collisions: `OUT=/private/tmp/claude-501/-Users-ianmacdonald-code-dams-physics/0958b9ad-36ad-42e5-abb6-32d34a812ceb/scratchpad/<you> python3 build.py`.
   Scratch files go under the session scratchpad, never in the repo.
8. `docs/academy/` is a separate site. Leave it alone; it only shares `seepage-solver.js`.
9. Shell quirks: `/bin/rm -f`, `/bin/ls`, `/usr/bin/grep`. Headless Chrome screenshots need an
   iframe wrapper page (see the task text); look at screenshots with the Read tool.
10. A real fork that is the user's to decide: make the smart assumption, do the work, and put
    `DECISION NEEDED: <question> — options: <a> / <b>` in your concerns.

### A.2 What the build does, in order

`python3 build.py` (and `OUT=<dir> python3 build.py`) does this. Every validation error is
collected; if there is any, the build prints all of them and exits 1 without writing outputs.
`DRAFT=1` downgrades the errors marked *(draft: warning)* to warnings.

1. **Read and validate `src/book.json`** against section B. Every `file` must exist.
2. **Assemble the markup.** Start from `src/body.html`. Replace `<!-- @book -->` with, in order: each
   front unit, the Prologue, then for each part its generated part opener (B.4) followed by its
   chapters, then the Epilogue, then each back unit. Expand `<!-- @include name.html -->` lines in any
   file (names resolve in `src/`, up to four levels deep, as today).
3. **Check each unit's root.** A unit file's first element must be
   `<section class="<kind>" id="<id from book.json>">` where kind is `front`, `prologue`, `chapter`,
   `epilogue` or `back`.
4. **Insert alias anchors.** For each alias `{ "id": "beach" }` insert
   `<a class="alias" id="beach" aria-hidden="true" tabindex="-1"></a>` as the first child of the unit's
   section; `{ "id": "x", "before": "elem-id" }` inserts it immediately before that element instead.
   An alias that collides with any other id is an error.
5. **Generate openers** (F.1): fill `header.opener[data-gen="opener"]` of every chapter, the Prologue and
   the Epilogue from `book.json` and the counts in step 7.
6. **Move answers to the back** (F.14): every `li.q > .q-answer` is moved, in document order, into the
   `#answers` section under a heading per chapter, wrapped as
   `<div class="ans" id="ans-<question id>"><p class="ans-k"><a data-ref="<question id>" data-form="num"></a> · Explore</p>…</div>`
   (the reference is resolved in step 8, after numbering), and replaced in place by
   `<p class="q-ans-link"><a href="#ans-<question id>">Answer</a></p>`.
7. **Number everything** (section D): figures, tables, worked examples, equations, films, questions,
   numbered sections, sidenote counters. Fill every `[data-num]` placeholder.
8. **Resolve references:** `a[data-ref]` (D.3), `a[data-cite]` and `cite[data-cite]` (A.4).
   Dangling ids and unknown cite keys are errors *(draft: warning, rendered as "?", but only for ids
   listed in some unit's `newIds`)*.
9. **Generate the back matter:** contents (B.5), answers (step 6), glossary data (A.5), case-file
   index (A.7), bibliography (A.4), errata (A.6).
10. **Film segments and transcripts** (F.13): validate `start`/`end` against `duration`; build each
    film block's transcript from its VTT, clipped to the segment.
11. **Global checks:** duplicate ids across the whole page; typed numbers in prose (D.5); `Step N`
    anywhere in `src/book/`; a `figure` without a `figcaption`; a numbered element without an id;
    `data-term` with no glossary entry; `data-n` with an empty or non-numeric text; the Polley guard
    (G.4).
12. **Scripts and styles.** CSS is `styles.css`, `styles-ground.css`, `styles-grains.css`,
    `styles-build.css`, `styles-tutor.css`, `styles-book.css`, then every `src/fig/*.css` sorted by
    file name. The app bundle is one IIFE, in this order: `app-core.js`, `app-glossary.js`,
    `app-ground.js`, `app-grains.js`, `app-zones.js`, `app-seep.js`, `app-build.js`, every
    `src/fig/*.js` sorted by file name, `app-book.js`, `app-tutor.js`, `app-film.js`. Each `src/fig`
    file wraps its code in its own named function (`(function figGripEnvelope() { … })();`), like the
    existing files.
13. **Data for the scripts.** Before the app script, emit
    `<script id="book-data" type="application/json">{…}</script>` holding
    `{ "refs": { id: { "label", "num", "kind", "unit", "title" } }, "units": [ { "id", "label", "n", "title", "question", "kind" } ], "glossaryExtra": { slug: [term, definition] }, "films": {…} }`.
14. **Write outputs:** `OUT/index.html`, `OUT/app.bundle.js`, `OUT/docs/index.html` (as today), the
    academy copy (as today), and two new git-ignored files for the tests:
    `OUT/build/book.html` (the assembled, numbered body markup, exactly what goes inside the page)
    and `OUT/build/book-data.json` (the same JSON as step 13).

While stage D has not happened yet, `build.py` ignores `book.json` (nothing references it), so
committing the manifest now changes nothing.

### A.4 Bibliography files

`src/book/bib/<key>.json` maps a citation key to an entry:

```json
{
  "foster2000": {
    "group": "papers",
    "short": "Foster, Fell & Spannagle (2000)",
    "authors": "Foster, M., Fell, R., Spannagle, M.",
    "year": "2000",
    "title": "The statistics of embankment dam failures and accidents",
    "container": "Canadian Geotechnical Journal 37(5): 1000–1024",
    "doi": "10.1139/t00-030",
    "url": null,
    "note": "Table 3 gives the failure shares; 124 failures to 1986, excluding failures during construction."
  }
}
```

- `group` is one of `books`, `papers`, `reports` (panel and investigation reports), `standards`
  (standards and guidelines), `bc-law` (BC legislation and regulators), `web`.
- Keys are global. If two files define the same key, the entries must be identical or the build
  fails. Use the canonical entries in Appendix 1 verbatim; add new keys only for works not listed.
- An entry may carry `"verify": "<what to check>"`. The build warns; `test-book.js` **fails** if a
  cited entry still has `verify`. Check it against the source (WebSearch or WebFetch), fill or
  correct the fields, and delete `verify`. Never invent a DOI, page number, volume or quote: leave a
  field `null` rather than guess.
- Cite in prose with `<a data-cite="foster2000"></a>` (renders `short`, links to `#bib-foster2000`)
  or `<a data-cite="foster2000">Foster and colleagues</a>` (keeps your words). In further-reading
  lists use `<cite data-cite="usbr1987"></cite>`, which renders the full entry.
- The bibliography renders each group alphabetically by `authors`, with "Cited in Ch. 4, 11"
  computed from where the key is cited.

### A.5 Glossary files

`src/book/glossary/<key>.json`:

```json
{
  "gauge-pressure": ["Gauge pressure", "Pressure measured above the pressure of the air. A tyre gauge reads it; this book uses it throughout, so the water surface is at zero."],
  "piping": { "replace": true, "entry": ["Piping", "…"] }
}
```

- A slug may be defined only by the unit Appendix 2 assigns it to. Defining a slug another unit
  owns, or one already in `GLOSSARY`, is a build error unless it is `{ "replace": true, … }` **and**
  Appendix 2 lists that replacement for your unit.
- `app-glossary.js` (machinery) merges `GLOSSARY` with `book-data.glossaryExtra` before it wires the
  tooltips and builds the list, and its "First met in" link reads the chapter label from
  `section[data-label]` ("First met in Chapter 4").
- Definitions: one or two plain sentences, conditions stated ("in still groundwater"), no forward
  spoilers, never mention Mount Polley.

### A.6 Errata files

### A.7 The case-file index

Every `figure.case-plate` (F.12) is indexed in `#case-files` as a row: dam, year, where, type,
chapter (linked), and mechanism from `data-mechanism`. For Mount Polley the mechanism cell reads
"See Chapter 13" (the plate carries `data-mechanism-safe="See Chapter 13"`; the index uses it).
Cases that appear only as prose (Stava, Merriespruit, Fundão, Brumadinho, El Cobre, San Luis, Lower
San Fernando, Oroville, Fort Peck, Revelstoke, Site C) are listed from the rows of
`tbl-two-dams-cases` and from `span.case-ref[data-case]` markers writers put on first mention.

### A.8 Text pins

`tests/test-figures.js` today pins sentences that carry corrected facts ("Facts the text states").
Stage D moves each pin to the unit whose text now holds the sentence, as
`tests/pins/<key>.js`:

```js
module.exports = {
  says:  [['takes almost the whole drop in head, from the reservoir level down to the downstream side', 'core takes the head']],
  never: [['from where it is pushed hard to where it is pushed less', 'head, not pressure']]
};
```

`test-figures.js` loads every pin file and checks it against the built page's plain text. A writer
who rewrites a pinned sentence keeps its fact, and updates the pin in the same commit to a string
from the new sentence that still states that fact. A pin is never deleted without an equivalent one.
Pins that check code (`app-build.js` mission text, `app-zones.js` cards, the glossary) stay in
`test-figures.js`. A pin file may also hold `markup: [[/regex/, 'label']]`, checked against the built
markup (for facts in an aria-label). In the plain text a keyed number reads as its digits, and a
generated reference as its label with spaces round it ("subject of Chapter 13 ."), so end a pin
before the punctuation that follows a reference.

### A.9 What the machinery built (stages C and D, as implemented)

- **`data-stub`.** Any element with `data-stub` is dropped from the page by the build; a unit whose
  root carries it is left out entirely (no contents entry, no refs). The skeletons use it for every
  planned but unwritten part (openers' "So far" and "can" lists, chapter ends, briefs' new sections,
  the Prologue, Epilogue, Preface, Plate 0, the toolkit, symbols, colophon). **To publish a part,
  remove `data-stub`.** The comments inside each stub point to the brief.
- **Openers and ends.** The build writes the opener's kicker ("Chapter 4 · Part I · Ground"), title,
  question and meta line into `header.opener` as `div.wide > div.chapter-head` (the old sheet head),
  before the writer's content; `p.ch-num` and the miniature are left to the layout stage (there is no
  `mini.svg` yet). Chapter ends are `<section class="ch-end col">`; the build fills
  `nav.next-card[data-gen=next]` with Next and Previous links.

### A.10 What the layout stage built (the design system, as implemented)

- **Grid.** `.col` is a plain block whose right padding is the margin column (38rem text, 2.5rem gap,
  15rem margin at ≥1100px), so sidenotes float out of their paragraphs as in Tufte CSS. Inside a
  `.col`, `figure.table`, `section.we`, `figure.fig`, `figure.case-plate` and anything `.wide` reach
  into the margin. Figures outside a `.col` are `.wide` (text plus margin) or `.full` (the six
  instruments, now marked so). Below 760px plates go full-bleed.
- **No sideways scrolling.** Every drawing fits its plate. `app-book.js` sets `--s` (rendered width ÷
  viewBox width) on each `svg.dwg`, and `styles-book.css` lifts small labels toward a floor (11px on a
  phone, 10.5px on a laptop) within a cap, so dense drawings don't collide. Every plate with a
  scrolling-era drawing (`.full`, or a `.svgwrap`/canvas) gets an **Expand** button below 900px: the
  figure itself moves into a full-screen dialog (drawing first and pinned, controls under it), turned a
  quarter turn on an upright phone, where labels reach 11px. SVG label sizes are set with `--fs` (not
  `font-size`) so the floor can work; new figure CSS must do the same.
- **The running section** is drawn once in `tools/bookmini.py` (one `<symbol>` per layer, stacked by
  depth) and placed in each opener (with "This chapter adds …" from `book.json`), each part opener,
  each Contents row and the running head. The Ch 7 concrete block sits right of the toe, not left.
- **Openers.** The build adds `p.ch-num` and the miniature (`div.opener-foot`); writers' epigraph,
  So far and "can" list sit between the generated head and foot.
- **Questions.** The tag and difficulty dots are drawn from `li.q[data-tag][data-level]` by CSS; do not
  type them. **Notes:** the markup of F.3 is unchanged; `app-book.js` turns each mark into a
  `<button aria-expanded>` on narrow screens. A Source note may name the source's own tables and
  figures ("Table 3"): the typed-number check skips `.marginnote[data-kind="source"]` and `<cite>`.
- **Running head and Contents dialog** (`#runhead`, `#toc-dialog`, generated from `#book-data`); the
  old index bar and `indexBar()` are gone. **Film posters** are HTML overlays (`app-film.js`), and
  `.film-marks button[data-t]` seeks.
- **Set the figure** accepts any control id: a range, a checkbox or select, or a group whose buttons
  carry `data-v`, `data-i`, `data-m`, `data-p` or `data-exp`. It clamps and reports an illegal value,

|---|---|---|---|

## E. The number manifest

### E.1 What gets a key

1. Every number the code computes: a figure readout, a solver result, a constant the code uses (the
   block's 20 kN, φ = 34°, concrete at 23.5 kN/m³, γw = 9.81).
2. Every result of arithmetic in a worked example or an answer (each line's result), even when the
   arithmetic is the writer's own (the definition then does that arithmetic from the code's inputs).
3. Givens that come from the code, the first time each appears in a worked example's Given line.

Not keyed: dates, chapter-internal counts ("three fixes"), small integers used as words, and numbers
from the literature, which carry a Source note instead (F.3). Illustrative numbers that no code holds
(the rate-of-rise mine, the spillway weir, the compaction test) are keyed in the chapter's own file
with their inputs written there as named constants and the word "illustrative" in the prose.

### E.2 Markup

```html
<span data-n="block.fs@a=25">1.45</span>
<span data-n="lab.q-lday">2,366</span> L/day per metre
<span data-n="darcy.share-pct@plug=1">99.996</span>%
<span data-n="ch03.core-years" data-n-sig="1">9</span> years
```

The span wraps the digits only; units and words stay outside.

### E.3 Key syntax

```
key   := ns "." name [ "@" arg ( "," arg )* ]
ns    := [a-z][a-z0-9-]*        a figure namespace (Appendix 4) or a unit key: ch01…ch13, pro, epi, front, back
name  := [a-z][a-z0-9-]*        ends with a unit suffix when the unit is ambiguous: -kpa, -mn, -kn, -m, -s, -lday, -pct, -deg …
arg   := [a-z][a-z0-9]* "=" [-+.0-9a-z]+
```

Examples: `depth.p-kpa@h=30`, `block.u-slide-kpa@a=10`, `bench.fos@preset=cored,found=weak,slope=3`,
`ch07.fs-phi35`.

### E.4 Definitions

```js
// tests/numbers/ch04.js
module.exports = {
  'ch04.face-deg-phi30': {
    doc: 'steepest face of φ′ = 30° sand with water seeping out parallel to it',
    f: (args, X) => Math.atan((X.G.COL.GS - X.G.COL.GW) / X.G.COL.GS * Math.tan(30 * X.deg)) / X.deg
  },
  'ch04.ic': { doc: 'critical gradient from the stress column’s unit weights', f: (a, X) => (X.G.COL.GS - X.G.COL.GW) / X.G.COL.GW }
};
```

- A definition's key may hold arguments with defaults: `'block.fs': { args: { a: 25, u: 0 }, f: ({ a, u }, X) => … }`
  answers `block.fs`, `block.fs@a=30`, `block.fs@a=30,u=2.5`. Argument values arrive as strings;
  convert them.
- `X` (from `tests/numbers/_lib.js`) holds the loaded pure blocks exactly as `test-figures.js`
  loads them (`X.G` app-ground, `X.C` app-core hydro and raise, `X.S` app-seep lab/pipe/uplift,
  `X.U` util), the solvers (`X.seep(opts)` and `X.bench(design)` with a per-process cache), and
  `X.deg`.
- `f` returns a plain number in the units the key names (`-pct` keys return percent, `-mn` keys
  meganewtons). Where the figure itself rounds before it shows a number (the "1,250 tonnes" readout
  rounds to tens), the definition returns the figure's rounded value.
- Writers add keys only in their own unit file, only in their own namespace. Figure namespaces
  (Appendix 4) live in `tests/numbers/figs.js`; a chapter that needs a figure value that is not
  there defines it under its own namespace.

### E.5 What `test-book.js` checks

For every `[data-n]` in the built page:

1. The key parses and has a definition (else fail: "no definition for …").
2. The text parses as a number: digits with `,` thousands separators, `.` decimals, a leading `−`
   (U+2212) or `-`, a trailing `%` (the value is then in percent), or the forms `a × 10⁻⁴` /
   `10⁻⁹` with superscript digits.
3. Rounding: the code's value is rounded half away from zero to the number of decimals shown (or to
   `data-n-sig` significant figures when present) and must equal the shown number exactly. For the
   `a × 10ⁿ` form the value is scaled by 10⁻ⁿ first and compared on the mantissa's decimals.

It also fails on a definition that throws or returns a non-finite number, and it prints (without
failing) a list of digit runs in worked examples and captions that carry neither a key nor a nearby
Source note, for the reviewer.

## F. Components, with the markup to copy

Every component below is styled by `styles-book.css` and, where it moves, run by `app-book.js`
(machinery). Writers copy the markup and change only text, ids and data.

### F.0 Page grid and widths

A unit's body is a sequence of `<div class="col">` blocks (prose, text column 38rem with a 15rem
margin column at ≥1100px) and figure-level siblings between them. Widths: no class = text column;
`.wide` = text plus margin; `.full` = the six big instruments only (`fig-grains`, `fig-raise`,
`fig-zones`, `fig-lab`, `fig-uplift`, `fig-build`). On phones (<1100px) everything is one column with
16px gutters and `.wide`/`.full` plates go full-bleed with an Expand button (machinery).

### F.1 Chapter opener (and Prologue, Epilogue)

Writer's markup, at the top of the unit file:

```html
<section class="chapter" id="ch-grip">
  <header class="opener" data-gen="opener">
    <blockquote class="epigraph">
      <p>Line of the epigraph.</p>
      <footer>Karl Terzaghi, <cite data-cite="terzaghi1929"></cite></footer>
    </blockquote>
    <p class="so-far"><b>So far.</b> Two or three sentences that pick up where the last chapter left the reader.</p>
    <div class="can">
      <p class="can-k">After this chapter you can</p>
      <ul>
        <li>work out the factor of safety of a block on a ramp, with and without water under it;</li>
        <li>…;</li>
        <li>….</li>
      </ul>
    </div>
  </header>
```

The build prepends `p.ch-num` (the numeral), `p.ch-kicker` ("Chapter 4 · Part I · Ground"),
`h2.ch-title` and `p.dek` (the `question`), and appends `svg.mini` (layers 1…`mini`) and `p.ch-meta`
("2 figures · 1 lab · about 35 min to read", plus "Film 5.1, 9 min" when there is a film; reading
time is main-text words ÷ 200, rounded to 5 min). Epigraph is optional: use one only where it is
earned, and only a real quotation from a source you can cite (G.5). The Prologue and Epilogue use
`class="prologue"` / `class="epilogue"`; they have no "can" list.

The running miniature: one drawing of an embankment section, 160 × 48 px, built from the `book.json`
`mini` layers (0 ground line; 1 heap; 2 water and pressure triangle; 3 phreatic line and a
standpipe; 4 σ′ arrows; 5 soaked zone shaded; 6 freeboard mark and spillway notch; 7 small concrete
block with uplift arrows; 8 a raise on the crest; 9 core and filter; 10 two flow lines and three
equipotentials; 11 toe filter and drain; 12 slip circle; 13 the 1 m workbench grid; 14 two
piezometers and a weir). It never shows a foundation layer.

### F.3 Notes: sidenotes and margin notes

```html
<label for="sn-grip-terzaghi" class="sn-ref"></label><input type="checkbox" id="sn-grip-terzaghi" class="margin-toggle"><span class="sidenote" data-kind="history">Karl Terzaghi worked out effective stress in Istanbul in the early 1920s and published it in <cite data-cite="terzaghi1925"></cite>.</span>
```

Unnumbered margin note (Source, Units):

```html
<label for="mn-grip-hd" class="mn-ref" aria-label="Source"></label><input type="checkbox" id="mn-grip-hd" class="margin-toggle"><span class="marginnote" data-kind="source"><a data-cite="horn-deere1962"></a>, Table 2.</span>
```

- `data-kind` is `history`, `curious`, `units` or `source`; CSS prints its label ("History", "For
  the curious", "Units", "Source").
- History and For the curious are numbered sidenotes; Source and Units are unnumbered margin notes.
- The note sits inside the `<p>`, right after the word it belongs to, and contains only inline
  markup (no `<p>`, `<ul>`, `<div>`). Ids: `sn-<slug>-<word>`, `mn-<slug>-<word>`.
- At ≥1100px notes float into the margin beside their line. Below that, every note is closed and
  the label is a tap target (the number, or ⊕ for margin notes); tapping opens it in a ruled block
  under the line. No JavaScript.
- At most six History, For the curious and Units notes per chapter. Source notes as many as the
  literature numbers need, at most one per paragraph.
- Nothing the argument needs goes in a note.

### F.4 Glossary span

`<span class="gl" data-term="effective-stress">effective stress</span>`. Mark a term at its first use
in each chapter (so a reader who starts at that chapter gets the tooltip), not every use. The slug
must exist in `GLOSSARY` or a glossary file (Appendix 2).

### F.5 Equation display

```html
<div class="eq" id="eq-grip-sigma">
  <span class="eq-body"><var>σ′</var> = <var>σ</var> − <var>u</var></span>
  <span class="eq-no" data-num></span>
</div>
<p class="eq-where"><var>σ</var> total stress, the weight of everything above, per square metre (kPa) · <var>u</var> pore pressure (kPa) · <var>σ′</var> effective stress (kPa)</p>
```

Set in the serif: variables in `<var>`, a true minus (−, U+2212), thin spaces (U+2009) around ×,
`<sub>`/`<sup>` for indices, `·` for multiplication of symbols. No MathJax, no code font. Each
chapter numbers its equations; reference them as `<a data-ref="eq-grip-sigma"></a>`. Inline maths
in a sentence uses `<var>` too, no box. The old `div.formula` boxes are replaced by `div.eq` in
stage E (the machinery keeps styling `div.formula` until then).

### F.6 Worked example

```html
<section class="we" id="ex-grip-block">
  <header class="we-head">
    <p class="we-k" data-num></p>
    <p class="we-t">How much water pressure slides the block?</p>

    <dt>Find</dt><dd>The factor of safety, and the cushion pressure at which the block slides.</dd>
    <dt>The idea</dt><dd>Friction comes from the part of the weight pressing into the ramp; the water takes some of that press away (<a data-ref="fig-block"></a>).</dd>
  </dl>
  <ol class="we-steps">
    <li><span class="we-eq"><var>N</var> = <var>W</var> cos 25° = 20 × 0.906 = <span data-n="block.N-kn">18.13</span> kN</span><span class="why">the part of the weight pressing into the ramp</span></li>
    <li><span class="we-eq">…</span><span class="why">…</span></li>
  </ol>

  <p class="we-check"><b>Check.</b> An order-of-magnitude or limiting case: at 0° the pull is zero and FS is infinite; at 34° with no water FS is exactly 1.</p>
  <p class="we-means"><b>What it means.</b> One or two sentences tying the result to the spine.</p>
```

  the why under the step on a phone.
- Every computed number keyed (E.1). Givens from the code keyed on first appearance.
- `Set the figure` is optional per example, required when a figure can show the example's state.


## G. Voice and craft

### G.1 The spine

> *Soil holds only as well as its grains press on one another, and the water between them can take that press away.*

It is printed on the title page (from `book.json`), stated as a promise in Ch 1, **earned in Ch 4**
(where σ′ = σ − u makes it provable: "Turn back to the title page and read the sentence there. You
can now prove it."), restated in each chapter's "What to remember" in that chapter's terms, and
qualified honestly in the Epilogue with `spineCoda`: overtopping, which with spillway and gate
failures accounts for about half of embankment-dam failures, is a different story. Never claim the
spine explains "every" failure.

### G.2 The voice

One plain, warm, expert voice: a sharp engineer who loves the subject, explaining it to a smart
friend at a table. Concretely:

- **Concrete before abstract.** A scene, a handful of sand, a number the reader can check, then the
  principle, then (if at all) the formula. No equation before the reader has seen what it describes.
- **Misconception first, then the test** (Ciechanowski): "One could assume…" or "Most people say…",
  then the figure that refutes it. At least once per chapter, on a belief beginners really hold.
- **Point the eye before explaining** (Ciechanowski's rhythm): set-up sentence ending in a colon →
  the figure → "Notice that…" → the explanation → the formula.
- **Say what nobody knows** (Feynman): nobody can see inside a dam; piezometers are pinpricks; 1.5
  is a convention, not a law; failure statistics are counts with overlapping categories.
- **Short declarative sentences, varied length.** Jargon explained at first use and marked with a
  glossary span.
- **Paragraphs pass the "therefore / but" test** (Nicky Case): each follows from the last by
  therefore or but, never by "and then".
- **Each chapter ends on a question** the next chapter answers.
- Canadian spelling, as the page already uses: metre, centre, colour, litre, -ize ("recognize"),
  "analyze". Dates as "4 August 2014". Numbers with comma thousands (12,263), a true minus (−),
  units after a space (kPa, kN/m³, m/s, L/day per metre of dam). Slopes: "2H:1V (two across for
  every one up)" at first use in a chapter, "2:1" after.
- Disasters with dignity: each toll stated once, sourced, plainly. No adjectives doing the work.

**Never write** (the course was just cleaned of these):

- negative parallelism: "It's not X, it's Y", "not just X but Y", "This isn't about X. It's about Y.";
- reflexive triplets (three items because three sounds good);
- "Here's the thing", "Let's dive in", "In this chapter we will…", "It turns out that";
- stacked em-dashes; use commas, colons and parentheses (an occasional single em-dash is allowed);
- inflated words: crucial, delve, robust, tapestry, testament, intricate, pivotal, seamless,
  landscape, realm, underscore, vital, key (as an adjective), leverage, unlock;
- rhetorical questions as filler (the opening question and the Next pull are real questions);
- tidy moral summaries at the end of paragraphs ("And that is why water matters.");
- exclamation marks; "simply", "just", "obviously", "of course".

### G.5 Citing

- Every number from the literature (a date, toll, volume, height, statistic, a design rule's value)
  carries a Source margin note next to it, citing a bibliography key, with the table or page when
  you know it.
- When you are not sure of a fact, check it with WebSearch or WebFetch against a primary or
  reputable source (panel report, agency, peer-reviewed paper) before you write it. The briefs mark
  facts that need checking with **verify**.
- Never invent a citation, page number, quotation, DOI or date. A quotation must be one you have
  read in the source. If you can't verify something, leave it out, or write around it, and say so in
  concerns.
- Paraphrase panel reports; quote at most a sentence, in quotation marks, with the source.

### G.6 Numbers the code computes

Use the key, never a typed copy (section E). When you round in words ("about a third"), the exact
keyed value must appear somewhere nearby (in the same paragraph, a worked example or a caption). If
the code's number looks wrong to you, do not change the code or round it away: report it in
concerns.
